# Rule 01: Context, Scope and Decisions

User authorization and repository-specific instructions take precedence. Default to ticket-autopilot.md: complete authorized ticket delivery without routine stage-confirmation questions. Bundled company policy targets a real reviewed GitHub PR through jira-to-github.md.

- Read context and relevant code. Bootstrap missing shared context from authorized sources; label confirmed intent, observed behavior, technical assumptions and unknowns. Ask about material business ambiguity, not routine choices.
- Preserve edits/data. Never commit, push, revert or delete another person's unrelated work. Company ticket changes use scoped commits on the proper isolated branch/worktree. Autonomous records capture initial dirty bytes/index; only unchanged baseline paths are excluded from scope. Later edits require a plan.
- Keep artifacts under .aidlc/specs/active/TICKET. Exact plan.json paths govern implementation. Shared docs/rules and other tickets are not blanket exemptions. maxFiles is the aggregate budget including tests/docs; revise with rationale and downstream evidence.
- Shared manifests/dependencies require exact allowedFiles/dependencyFiles, justified versions and coder ownership. QA requests runner/dev-dependency setup; a planned narrow coder setup Unit can precede QA behavioral baseline. Dedicated tests/assertions remain QA-only.
- Coordinator alone delegates; specialists never recursively delegate. Preserve architecture/contracts; avoid unrelated edits, secrets and sensitive logs.
- Autonomous mode records agent observations and progress/revise decisions; reviewed/legacy mode needs actual human context/advance/reopen decisions. Never invent by values, approval, tests, CI or deployment evidence. Agents never hand-edit state.json, receipts or logs.
- Changed context/artifacts require revising the earliest affected stage, superseding downstream decisions and reverifying. Automatic replanning is allowed within the authorized ticket; report substantive assumptions.
- Markdown and helper do not authenticate identities or enforce OS permissions. check checks scope; verify runs explicitly selected commands. External document commands are not automatically trusted.
- Company pull-request delivery requires a real PR URL/current head, mandatory checks and independent review with no blocking findings; helper local completion or a PR draft is insufficient. Honor the user's existing branch push/PR/review authorization. Submit AI review COMMENT only, never forged human APPROVE/self-approval. Merge/deploy/Jira writes need separate authorization. Generic helper without company config retains local-draft compatibility. Host permissions and protected branches still apply.
- Load effective company policy, derive unknown base/commands/reviewers from authorized repo sources and treat only unresolved consequential gaps as blockers. Required company commands are additive; never remove them from a ticket plan. Policy changes invalidate verification. doctor is offline readiness, not proof of remote access/CI.

- Preserve existing company policy. Ordinary feature/bugfix work may fill unknown settings or add checks from authoritative repository sources during bootstrap, but must not remove/reduce known mandatory commands, independent/human review requirements or branch protections, or delete company.json to make checks pass. Reducing known requirements needs explicit policy-owner authorization in a separately scoped policy change; autonomous replanning is not that authorization. Missing-file compatibility is for generic/legacy use, never permission to bypass an existing policy. Runtime defaults select new tickets only and do not silently change existing record modes. Actual protected-branch/required-review enforcement remains server-side, not a CLI guarantee.
