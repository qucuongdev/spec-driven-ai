# Rule 02: Evidence and Test Integrity

- For new or changed business logic and bugfixes, derive unit tests from AC/spec before production implementation and run a valid behavioral red baseline first. Record exact command, test paths, AC mapping, source revision and dirty state, actual exit and assertion-failure evidence in test-plan.md. Syntax/import/fixture/setup failures are not behavioral red. Coder then implements to green and auditor independently checks test integrity and results; never derive expectations from coder output just to pass. Refactor characterization may pass before changes. For genuinely unautomatable cases, document the concrete reason and alternative verification for coordinator/auditor assessment, without a routine user approval gate. A narrow pre-QA setup Unit may change runner/dependencies/test wiring only and must not implement new business logic.
- Not every test must fail. Syntax/import/setup/fixture failures are not valid behavioral red evidence. Plan missing tooling as a coder-owned setup Unit and have QA rerun the baseline.
- QA alone edits dedicated test paths declared in allowedFiles and testFiles, including fixtures, snapshots and dedicated test configuration. Coder never weakens assertions/expected results. Mixed manifests are coder-owned for explicitly planned setup/dependencies/wiring without assertion edits.
- Correct wrong tests through QA with rationale and assessment, revising affected stages. Never skip tests, suppress exits or reduce coverage to hide defects.
- Coordinator delegates fresh contexts where supported; specialists do not delegate. Otherwise disclose the fallback and never claim independent four-agent review; company completion waits for actual independent review. Harness controls, not Markdown, enforce write isolation.
- Record real commands, exits, source state, logs, existing versus new failures and limitations. Helper fingerprints current tracked/nonignored files, real initialized submodules recursively and effective policy plus plan/context; relevant edits/source commits require fresh verification. Markdown has no automated fingerprint enforcement.
- Ignored output, runtime/environment, external services and linked contents are not fingerprinted; assess relevant changes. A run editing nonignored files is stale: review output and rerun on a stable tree.
- check passing does not prove tests/security pass. Company delivery requires independent review of exact current PR HEAD, real required CI/review evidence and no blocking findings. Older-SHA checks/reviews, local verified draft and AI COMMENT do not prove these conditions. Never forge human APPROVE or self-approval, and never promise zero regressions.
