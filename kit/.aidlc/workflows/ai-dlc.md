# Workflow: AI-DLC from Project Context to PR and Operations

This is a portable adaptation of AWS AI-DLC, not the original AWS engine. Default to ticket-autopilot.md for autonomous ticket delivery, using jira-to-github.md under the bundled company pull-request policy. Read the rules first. Choose Markdown tracking or the optional local helper for each ticket; neither requires package installation or plugin registration. Resume from tracker.md in Markdown mode, or `node .aidlc/tools/cli.js status TICKET` in helper mode. Never invent approvals.

In Markdown mode, copy .aidlc/specs/templates/MANUAL_TRACKER.md to .aidlc/specs/active/TICKET/tracker.md and copy the applicable stage outputs from .aidlc/specs/templates/intent. Record actual decisions, source revisions and command results manually. No state.json or helper commands are required. When approved inputs change, mark downstream decisions superseded, reopen the affected stage and reverify. The helper commands below apply only to helper mode; see .aidlc/docs/USER_GUIDE.md for both modes.

Only the main coordinator dispatches specialists; specialists never spawn/delegate other agents. It coordinates four specialists with separate contexts: architect -> qa-tester -> coder -> auditor. Load the matching .aidlc/agents/ prompt and exact write scope before dispatch. The coordinator owns bootstrap/intake/context, other unassigned stages, handoffs and mode-appropriate decisions. It must not bypass specialist restrictions. Follow the active profile only. Without native subagents, use available separate sessions or continue a disclosed fallback for preparation; role switching is not independent review and cannot complete the company independent-review requirement. See .aidlc/docs/USER_GUIDE.md#multi-agent-collaboration. Markdown prompts and the CLI neither start model processes nor enforce a filesystem sandbox.

1. Bootstrap project context: document the business overview, glossary, rules and architecture. Autonomous mode records sourced agent observations; reviewed mode requires the responsible owner's actual acknowledgement.
2. Intake: capture the actual ticket link or content and select feature, bugfix, refactor or express. Create a manual record or use the optional helper's `new` command. Bootstrap context before autonomous new so copied setup/context files are captured in the initial dirty baseline.
3. context: load the project overview and read the relevant domain references. Check sources and unresolved questions. Use `context --agent coordinator --note ...` in autonomous mode; reviewed mode uses `context --by ... --note ...` for actual supplied human decisions only.
4. framing (feature) [Owner: architect]: clarify the business goal, feasibility, scope and decisions requiring human input.
5. discovery (except express) [Owner: architect]: inspect existing code, establish the baseline and assess the impact of the change. For greenfield work, record N/A with a reason.
6. requirements [Owner: architect]: define the specification, acceptance criteria (AC), business rule IDs, contracts and invariants. Resolve business questions that would block implementation.
7. plan [Owner: architect]: produce an appropriately detailed design, Units and dependencies. Set exact paths, maxFiles and verificationCommands in plan.json, retaining additive company requiredCommands and real base/review conventions. Explain test and dependency changes. Record the plan checkpoint before changing code.
8. tests [Owner: qa-tester]: define the test strategy and relevant baseline checks. For new/changed business logic and bugfixes, derive unit tests from AC/spec and run valid behavioral red before production implementation, recording exact command/test paths/AC/source revision; use passing characterization for refactors. Genuinely nonautomatable cases need concrete rationale and alternative verification assessed by coordinator/auditor. Do not require every new test to fail. Missing mixed-manifest/tooling setup may use a narrow planned coder setup Unit before QA reruns a valid behavioral baseline.
9. implement [Owner: coder]: implement, run development checks and record each Unit. Formal independent verification belongs to auditor. Avoid unrelated changes. Record completed Units and actual checks in implementation.md; the CLI does not schedule Units.
10. verify [Owner: auditor]: run the planned project commands and retain actual logs/results. In helper mode, use `verify TICKET --command "..."` to record exits and fingerprints. In Markdown mode, record the source revision and working changes manually without claiming hash enforcement. Review the complete diff, test quality and AC mapping. Complete verification.md and independent review.md for the exact final source HEAD, retaining real command evidence.
11. pr [Owner: auditor]: draft pr.md and review.md for the exact candidate. Coordinator uses existing authorization to push scoped company branch changes, find/reuse the matching repository/base/head PR or create it once, publish labeled AI review COMMENT, request known reviewers and inspect required CI/review threads. Route fixes through owners, reverify/repush and rereview latest SHA. Never forge human APPROVE or author self-approval. Record actual PR URL/head/checks/review in delivery.md. Company completion requires current required checks/review and no blocking findings; local pr.md/helper completion cannot prove remote facts. Generic local-draft policy may stop at verified draft. Do not merge automatically.
12. deploy/feedback (except express): proceed after the release decision. Record deployment evidence, operational results, lessons and knowledge updates. Company delivery stops at the completed reviewed PR, not merge/release. deploy/feedback require separate authorization; no automatic Jira comments/status transitions.

Each stage requires complete outputs/evidence. Autonomous coordinator decisions use tracker.md or `progress TICKET --agent coordinator --note "..."`; use revise to invalidate affected downstream work. Reviewed mode, including legacy records without mode, retains actual human advance/reopen --by decisions. Neither identity is authenticated. Never fabricate human approval. Git history and PR review remain team controls.

See `.aidlc/docs/WORKFLOW.md` for diagrams and the AWS mapping, and `.aidlc/docs/USER_GUIDE.md` for commands.
